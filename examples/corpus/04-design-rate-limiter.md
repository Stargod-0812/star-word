# 限流器选型 — 我们为什么不用令牌桶

> 元注释：示范气-03（明确判断 + 反 default best practice）、气-06（用人话）。

---

API 网关限流我们选了滑动窗口计数器，没选业界默认的令牌桶。理由：业务需要「精确秒级配额」，令牌桶给不了。

## 令牌桶的语义不是我们要的

令牌桶限的是**长期平均速率 + 突发容量**。在 1 秒窗口里，配额 100 QPS 的接口可能放进去 150 个请求，因为桶里攒了 50 个 token。这对大多数 API 没问题——总量控制住就行。

但我们对接的是金融业务，合规要求「单接口任意 1 秒窗口内不超过约定配额」。监管查的是任意 1 秒，不是平均 1 秒。令牌桶的突发容量在合规口径下就是违规。

## 滑动窗口计数器

实现：每个 key 用 Redis sorted set 存最近 1 秒的请求时间戳，每次请求 `ZRANGEBYSCORE` 数当前窗口，超过配额拒绝。

成本：每次请求 2 次 Redis 操作（ZADD + ZRANGEBYSCORE）。延迟 P99 约 1.5ms。我们的链路本来就有 200ms 预算，1.5ms 可接受。

## 为什么不漏桶

漏桶平滑流量但不能拒绝瞬时高流量——超过桶容量的请求要么排队要么丢，业务上要给清晰拒绝码。漏桶的「等待」语义跟我们的同步 API 模型不符。

## 取舍承认

滑动窗口的 Redis 成本比令牌桶高 3 倍。日常成本多花 8000 元/月。这笔钱换合规审计能过，划算。

如果场景是普通 API 限流（不查合规、能接受 burst），令牌桶仍是更好的选——内存里实现就行，不用 Redis。**选型的关键不是「哪个最好」，是「哪个匹配你的口径」**。
