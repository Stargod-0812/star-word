# 缓存击穿事故复盘 — 2026-04-12

> 元注释：示范气-05（信息密度）、气-04（看本质——是限流问题不是缓存问题）、式-08。

---

热门商品页缓存过期那一刻，1.2w QPS 直接打到数据库，从库 CPU 100%，主从延迟 8 分钟，相关业务全挂 14 分钟。

## 时间线

- 14:00:00 缓存 TTL 到期
- 14:00:00.3 first miss 触发回源
- 14:00:00.5 后续 ~1.2w 请求并发回源（无任何抑制）
- 14:00:01 主库 CPU 90%，从库延迟从 50ms 涨到 2 秒
- 14:00:30 从库延迟 1 分钟，订单读路径大面积超时
- 14:08:00 监控告警触发，on-call 介入
- 14:14:00 限流 + 重新预热缓存，恢复

14 分钟里订单系统损失约 240 万订单。

## 根因

不是缓存设计的问题，是回源没限流。

互联网流传的「缓存击穿用 mutex / single flight」方案我们写了，但是两年前。后来一次重构，回源逻辑被搬到新模块，mutex 没跟着搬。这次 incident 之前的 6 个月里，所有热 key 续期都是「过期 → N 个并发回源 → 抢着写回」状态，单纯因为流量不够大没出事。

## 修复

短期：所有缓存回源加 single flight，同 key 同时只允许 1 个回源 goroutine，其他 wait。20 行代码。

中期：把 single flight 抽到 cache 装饰器层，业务代码不用管。后续新模块自动有保护。

长期：mock 缓存击穿做混沌测试，每月跑一次。这次根因是「保护代码沉睡两年没人验证」，不补混沌测试还会有下次。

## 不归咎个人

那次重构是我做的，code review 我也参与了。问题是当时 review 的人都没把「回源限流」当默认要求查。以后 cache 模块的 PR 模板加一行 checklist：「回源是否有 single flight 保护？」。流程兜底比记忆兜底可靠。
